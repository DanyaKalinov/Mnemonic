# Дизайн: многопользовательская архитектура Евы

> Дата: 2026-09-09. Статус: согласован с владельцем (итог брифа).
> Покрывает обе итерации; **итерация 1** — перевод владельца на локальный
> мозг, **итерация 2** — многопользовательская маршрутизация и онбординг.

---

## 1. Контекст и цель

Cегодня Ева работает так: Telegram-бот (`brain bot/`) разбирает команды
`/eva` (regex + Gemini-фолбэк) в структурированные `{action, params}`,
шлёт их единственному desktop-агенту владельца (`eva_agent/`) по
WebSocket, агент исполняет и возвращает результат. Один агент, один
владелец, **мозг — Gemini на сервере**.

Цель новой архитектуры — Ева как **личный ИИ-помощник у каждого
пользователя своего ПК**:

- **Мозг переезжает на ПК** — когда ПК онлайн, думает локальная модель
  (Qwen2.5-VL 7B через Ollama). Облако (Gemini) держим, но только там,
  где оно реально нужно.
- **Локальный агент = полноценный второй интерфейс** — тот же набор
  функций, что у Telegram-бота: память, напоминания, ask_web, действия.
  Общаться с агентом можно голосом (wake word) и чатом в приложении.
- **Память течёт в обе стороны** — сервер инъектирует контекст агенту,
  агент сохраняет новые факты в облачную память. Память едина для всех
  каналов и видна с телефона.
- **Напоминания двухканальные** — срабатывают и в Telegram, и в
  приложении, даже если ПК выключится до срабатывания.
- **Маршрутизация по пользователям** — итерация 2: `user_id → его агент`.

## 2. Принятые решения (итог обсуждения)

| # | Решение | Выбор |
|---|---|---|
| 1 | Облако остаётся целиком | Render + Supabase + Chroma + Gemini. Память per-user хранится в облаке. |
| 2 | Роль Gemini | Пишет тексты напоминаний; отвечает за чат, когда ПК агента **офлайн**. Когда ПК онлайн — думает локальная Qwen2.5-VL. |
| 3 | Локальная модель | Одна для всех: **Qwen2.5-VL 7B** (чат + зрение), скачивается при установке (~5 ГБ), min ~8 ГБ ОЗУ. |
| 4 | Привязка нового юзера | Одноразовый код из бота → вводится в приложении. (Итерация 2; твой текущий агент мапится на тебя без изменений настроек.) |
| 5 | Голосовой стек агента | Оставить как есть: Vosk (wake word) + Groq Whisper (STT) + edge-tts (TTS). Полный локальный голос — отдельной задачей позже. |
| 6 | Этапирование | Сначала владелец один (И1), потом многопользовательский онбординг (И2). |
| 7 | Чат в приложении | Добавляем поле ввода: приложение — третья точка входа (Telegram / голос / приложение), отвечает агент. |
| 8 | Память | Двусторонняя: сервер→агент (контекст в каждое сообщение), агент→сервер (memory_add / memory_search). |
| 9 | Напоминания | Хранятся в облаке; доставка в Telegram **и** в приложение; при ПК офлайн — только Telegram. |

## 3. Целевая архитектура

```
┌───────────────────────────────┐        ┌───────────────────────────────────┐
│  ОБЛАКО (Render, 24/7)        │  WS    │  ПК ПОЛЬЗОВАТЕЛЯ (eva_agent/)      │
│   brain bot/                  │◄──────►│                                    │
│                               │        │  • Qwen2.5-VL 7B (Ollama) — МОЗГ   │
│  • Telegram-бот (aiogram)     │        │    онлайн: чат + зрение + разбор   │
│  • Маршрутизация user_id→агент│        │  • Руки (actions.py): файлы, apps, │
│  • Память Supabase+Chroma     │        │    UI, мышка, громкость, питание   │
│    (изол. по пользователю)    │        │  • Cерверные функции на запрос:    │
│  • Gemini: тексты напоминаний │        │    напоминания, память, ask_web    │
│    + офлайн-чат               │        │  • Голос: Vosk + Groq + edge-tts   │
│  • Разбор команд офлайн       │        │  • Чат-вкладка в pywebview UI      │
│  • Подтверждение разрушит.    │        │    (поле ввода + лента сообщений)  │
│    действий (всегда в Telegram)│        │  • Windows-уведомления напомин.    │
└───────────────────────────────┘        └───────────────────────────────────┘
```

**Кто думает — определяется состоянием агента:**
- **ПК онлайн** → сообщение из любого канала уходит агенту по WS вместе с
  памятью-контекстом; локальная модель отвечает и/или действует. Gemini
  к этому чату не подключается.
- **ПК офлайн** → отвечает Gemini на сервере (как сейчас). Если команда
  относится к действиям на ПК — сервер отвечает «ПК выключен, выполню
  при подключении» и кладёт команду в очередь.

## 4. Компоненты и обязанности

### 4.1 Облако (`brain bot/`)
- `eva_ws.py` — новый контракт WS (см. §5), привязка агента к
  `user_id`, досылка очереди.
- `eva_agent_registry.py` — `user_id → {ws, agent_id}`. В И1 одна запись
  (owner→default), структура уже многоместная.
- `eva_engine.py` — перестраивается: онлайн = ретранслятор текста агенту;
  офлайн = старый конвейер разбора (regex + Gemini) + guard «ПК выключен».
- `memory.py` / Chroma — изолировать по `user_id`; добавить:
  инъекцию контекста в исходящие `chat`, обработку `memory_add` /
  `memory_search` от агента.
- `ai_core.py` — остаётся для офлайн-чата, ask_web (Tavily+Gemini) и
  текстов напоминаний.
- `handlers.py / bot_commands.py` — точки входа Telegram; ничего не ломаем.

### 4.2 Desktop-агент (`eva_agent/`)
- `local_brain.py` (**новый**) — клиент Ollama: чат, разбор utterance →
  план (ответ / локальное действие / облачное действие), зрение
  (описание скриншота/фото). Whitelist действий берёт из `actions.py`.
- `ws_client.py` — новые типы сообщений (§5); поддержка ответов в
  каналы; обработка уведомлений-напоминаний.
- `app.py` + `ui/index.html` — новая вкладка «Чат» (поле ввода + лента);
  область уведомлений-напоминаний; индикатор онлайн/офлайн.
- `actions.py`, `voice.py` — **не меняются** (кроме того, что `voice.py`
  теперь зовёт `local_brain` вместо отправки текста серверу и обратно —
  точнее: голосовой текст идёт тем же путём, что и чат, см. §6).

## 5. Новый WS-контракт (дельты к текущему)

Существующие типы (`command`, `result`, `speak`, `voice_command`)
остаются и используются для подтверждаемых локальных действий.
Добавляются:

**Сервер → агент**
| Тип | Назначение |
|---|---|
| `chat` | `{message_id, text, origin: telegram\|app\|voice, memory:[{text, score}]}` — сообщение с инъекцией памяти (top-5). Origin=voice для озвучки ответа. |
| `orchestrate_step` `{request_id, action, params}` | Завершённое подтверждение разрушительного действия → агент исполняет (обратная совместимость с `command`; можно использовать `command` напрямую — см. §6). |
| `cloud_result` `{request_id, status, result}` | Ответ на облачное действие агента (напоминание сохранено / память сохранена / ask_web-ответ). |
| `reminder` `{reminder_id, text, at}` | Сработавшее напоминание → уведомление в приложение + необязательная озвучка. |

**Агент → сервер**
| Тип | Назначение |
|---|---|
| `chat_result` `{message_id, kind: answer\|actions\|error, text, image_base64?}` | Итог обработки сообщения чата: либо текст-ответ, либо сообщение об исполнении локальных действий, либо ошибка. Сервер доставляет результат в исходный канал (Telegram / приложение) и, если origin=voice, запускает озвучку. |
| `confirm_request` `{message_id, local_steps:[{action, params, description}], voice?}` | Агент обнаружил разрушительное локальное действие → сервер шлёт кнопки ✅/❌ в Telegram **всегда**, независимо от канала (граница безопасности). При ✅ — шлёт агенту исполнение; результат доставляется во все активные каналы сообщения. |
| `cloud_action` `{request_id, action, params}` | Облачное действие агента: `create_reminder` / `memory_add` / `memory_search` / `ask_web`. Сервер исполняет, отвечает `cloud_result`. |
| `memory_add` | См. `cloud_action`; вынесен явно для читаемости в §7. |

**Единый whitelist на агенте** (взято из `actions.py`) делится по месту
исполнения:

| Локально (агент) | Облачно (сервер по `cloud_action`) |
|---|---|
| file/ops, open_file/folder, apps, UI (pywinauto), mouse, volume, power, screenshot, web_search (открыть браузер/сайт) | `create_reminder`, `list_reminders`, `memory_add`, `memory_search`, `ask_web` |

## 6. Поток данных по каналам

**Единый принцип: любой текст (Telegram, голос, чат в приложении)
становится сообщением, идущим на агента; онлайн-мозг — локальная модель.**
Различие каналов — только в доставке ввода и вывода (медиа).

### Telegram, ПК онлайн
1. `/eva текст` → сервер ищет в Chroma top-5 памяти → `chat`.
2. Агент: Qwen2.5-VL строит план:
   - **просто ответ** → `chat_result kind=answer` → сервер шлёт ответ в тот chat.
   - **безопасное локальное действие** → исполняет сразу → `chat_result kind=actions`.
   - **разрушительное локальное действие** → `confirm_request` → кнопки в
     Telegram → при ✅ сервер шлёт существующий `command` → агент исполняет
     → `result` → сервер уведомляет.
   - **облачное действие** → `cloud_action` → сервер исполняет →
     `cloud_result` → агент формулирует ответ → `chat_result`.

### Голос (wake word «Ева»), ПК онлайн
Как сегодня: Vosk ловит слово → Groq транскрибирует → текст. **Дельта:**
текст уходит не как `voice_command` в старый конвейер сервера, а тем же
`chat`-путём (origin=voice). Цепочка идентична Telegram, плюс: ответ
озвучивается (edge-tts), и копия результата дублируется в Telegram для
истории.

### Чат в приложении, ПК онлайн
Текст из поля ввода → `chat` (origin=app) → мозг на агенте → ответ
возвращается в ленту приложения по WS как `chat_result` → UI рисует
пузырь. Подтверждение разрушительных действий — по-прежнему кнопкой в
Telegram (граница безопасности не зависит от канала).

### Любой канал, ПК офлайн
Сервер сам: parse → если действие — «ПК выключен, выполню при
подключении» (команда кладётся в очередь) ; если вопрос/разговор — Gemini
отвечает как сейчас (память, ask_web). Приложение офлайн не работает (ПК
выключен) — Telegram остаётся единственным каналом, это и есть смысл
держать облако.

## 7. Память — двусторонняя

- **Сервер → агент:** на каждое `chat` — инъекция top-5 релевантных
  записей по эмбеддингу текста (один вызов Chroma, дёшево). Контекст
  попадает в промпт Qwen2.5-VL.
- **Агент → сервер:** локальный мозг сам решает, какой факт из разговора
  стоит сохранить → `memory_add {text, tags?}` → сервер эмбеддит и
  кладёт в Chroma пользователя. Активный вопрос «что я записывал про X»
  → `memory_search {query}` → `cloud_result` с записями → агент отвечает.
- Данные изолируются по `user_id` (уже намечается: колонка `user_id` в
  таблицах памяти/команд; в И1 заполняется только для владельца).
- Черновик фактов «не забудь про X» из приложения/голоса тоже попадает в
  память этим же путём — никаких отдельных каналов.

## 8. Напоминания — двухканальные

1. «Напомни через 15 минут вынести мусор» из **любого** канала →
   мозг агента → `cloud_action create_reminder` → сервер сохраняет в
   Supabase (сработает, даже если ПК выключится).
2. При срабатывании сервер шлёт: **Telegram-сообщение** (существующий
   канал) + **`reminder` агенту** → приложение показывает
   Windows-уведомление и (опция) озвучивает голосом Евы.
3. Текст напоминания пишет **Gemini** (как выбрано владельцем), даже если
   команда пришла с локального мозга.

## 9. Подтверждение разрушительных действий

Принцип не меняется: **сервер остаётся арбитром.** Локальный мозг может
*предложить* разрушительное действие — но исполняется оно только после
явного тапа ✅ в аутентифицированном Telegram-аккаунте владельца. Это
защищает от того, что посторонний голос/человек за ПК что-то сломает.
Список требует подтверждения — прежний (`delete_file`, `edit_file`,
`power_action`, `close_app`, move/copy и т.п. по `requires_confirmation`).

## 10. Обработка ошибок и краевые случаи

| Ситуация | Поведение |
|---|---|
| Ollama не запущена / модель не скачана | При первом запуске приложение показывает «поднять мозг» (`ollama pull qwen2.5vl:7b`) из UI; в ответе агенту — «мозг ещё не поднят, следующей командой сделаю после настройки». |
| Qwen2.5-VL вернула мусор/не валидный план | Фолбэк: агент отвечает текстом «не уверен, переформулируй», без действий. |
| WS оборвался | Как сегодня: переподключение с задержкой, команда остаётся в очереди. |
| Агент офлайн, команда-действие | Сервер: «ПК выключен, выполню при подключении» + в очередь. |
| Напоминание при выключенном ПК | Доставка только в Telegram. |
| Дупликаты памяти | В И1 без сложной дедупликации — одна запись факта; итерации памяти отдельно. |

## 11. Границы итераций

**Итерация 1 — владелец на локальном мозге (текущая цель):**
- Сервер: ретрансляция `chat` агенту + инъекция памяти; офлайн-путь с
  guard; обработка `chat_result`/`confirm_request`/`cloud_action`;
  изоляция данных по `user_id` (пока один).
- Агент: `local_brain.py` (Qwen2.5-VL), новые WS-типы, вкладка «Чат»,
  уведомления-напоминания в приложении.
- Пайплайн подтверждений и голосовой стек — без изменений.

**Итерация 2 — многопользовательность:**
- Привязка: `/eva_pair` → одноразовый код → ввод в приложении → WS
  привязывается к `user_id`.
- Маршрутизация по `user_id`; таблица агентов в БД; онлайн/офлайн статус
  на пользователя; онбординг новых юзеров (доступ через `eva_access`).

## 12. Безопасность

- WS-подключение авторизуется секретом агента (И1 — прежним
  `EVA_AGENT_SECRET`; И2 — одноразовым кодом привязки, привязанным к
  `user_id`).
- Разрушительные действия — только через кнопку в Telegram владельца.
- Память/данные изолированы по `user_id`; одна модель на всех, но
  контекст строго свой.
- Приватность мышления: при ПК онлайн тексты сообщений идут на агента
  через сервер (ретрансляция); в долговременную облачную память попадает
  только то, что локальная модель сама решила сохранить.

## 13. Тестирование

- **Юнит (сервер):** инъекция памяти (мок Chroma), обработчики новых
  WS-типов, офлайн-guard, `cloud_action` → корректный `cloud_result`.
- **Юнит (агент):** контракт `local_brain` (мок Ollama): фразы → план
  (ответ/действие/облако/подтверждение) для всего whitelist.
- **Интеграция руками (ПК владельца):** `ollama pull qwen2.5vl:7b`;
  команды из Telegram/приложения/голоса онлайн и офлайн; скриншот-вопрос;
  напоминание «через 15 минут» с проверкой доставки в Telegram+приложение.
- Существующие тесты (`test_reminder_parser.py`,
  `test_eva_command_parser.py`) должны остаться зелёными — разборщик
  остаётся для офлайн-пути.

## 14. Что НЕ входит (зафиксировано ранее)

- Биометрия лиц, постоянный мониторинг экрана, полный локальный голос,
  автозапуск с Windows, сборка `.exe`, Wake-on-LAN.
- Итерация 2 (привязка вторых пользователей) — отдельный цикл после
  обкатки И1 на владельце.
