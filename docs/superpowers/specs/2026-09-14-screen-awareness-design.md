# Дизайн: непрерывное осознание экрана (двухъярусная картина)

> Дата: 2026-09-14. Статус: согласован с владельцем (брейншторм в чате).
> Вариант А — двухъярусная картина экрана. Реализация в `eva_agent/`,
> схема взаимодействия с сервером (`brain bot/`) не меняется.

---

## 1. Контекст и цель

Сегодня агент «видит» экран только по запросу: пользователь пишет
команду, локальный мозг (Qwen2.5-VL 7B) может выбрать внутреннее действие
`look_at_screen`, агент делает скриншот и спрашивает vision-модель, что
видно (цикл «взгляд», `_resolve_local_plan` в `ws_client.py`). Между
запросами у агента нет картины экрана, и каждый ответ о экране платит
цену живого скриншота + VLM-вызова (1–3 сек).

Цель (согласовано с владельцем):

1. **Мгновенные ответы о экране** — «что сейчас открыто?», «какой сайт
   третий?» — без задержки живой съёмки.
2. **Следить за конкретным** — по заданию наблюдать за
   окном/процессом/сайтом и уведомлять об изменении
   (появление/исчезновение/изменение).
3. **Лучший контекст для команд** — команды «открой вторую вкладку»,
   «закрой этот чат» работают точнее благодаря постоянной картине.

Явно **НЕ цель** (владелец отклонил): самоинициирование — агент не
вмешивается без запроса, кроме явно заданных watch-правил.

## 2. Ключевые ограничения и решения

| # | Решение | Выбор |
|---|---|---|
| 1 | Непрерывный VLM-анализ каждого кадра | Невозможен/бессмыслен: 7B vision круглосуточно займёт GPU. Осознание = два яруса. |
| 2 | Ярус 1 (дёшево, всегда) | Фоновый цикл кадра ~1с + отслеживание активного окна + пиксель-дифф. Без LLM. |
| 3 | Ярус 2 (дорого, по требованию) | VLM-описание: по запросу при протухшем кэше + медленный фоновый refresh подписи. |
| 4 | Свежесть «мгновенного ответа» | TTL подписи-кэша ~12с; фоновый refresh ~45с. Отклик «из головы», глубокий взгляд — по требованию. |
| 5 | Watch («следить за конкретным») | Правила локальные (JSON агента, переживают перезапуск); уведомление — существующим путём «агент → сервер → Telegram + приложение». |
| 6 | Приватность | Кадры только в RAM; на диск не пишутся; ПК не покидают. |

Железо владельца (замерено 2026-09-14): RTX 5060 Laptop 8GB
(Ollama может использовать CUDA) + AMD 780M iGPU, Ryzen 7.
VLM-вызов ~1–3 сек.

## 3. Архитектура: два яруса

### 3.1 Ярус 1 — `screen_watcher.py` (новый модуль)

- Фоновый поток `ScreenWatcher`, стартует из `app.py`
  (по образцу `start_brain_background`).
- Цикл с интервалом `frame_interval` (default 1.0с):
  - `ImageGrab.grab()` → уменьшенная копия (ширина ≤ 320px, grayscale) →
    перцептивный хэш/дифф против предыдущего кадра.
  - Магнитуда диффа ≥ порога → событие «значимое изменение»
    (`change_ts`, `magnitude`). Порог отсекает курсор, мигание каретки.
  - Смена активного окна — Windows API (foreground window + title/class,
    машинерия из `actions.py`) → событие `focus_change`.
- Держит `ScreenState` (в памяти):
  - `active_window {title, class, hwnd, rect}`;
  - `last_change_ts`, `last_magnitude`;
  - `caption_cache {text, ts}` — выход яруса 2;
  - ring-buffer последних событий (≈64: focus_change / значимый дифф);
  - `screen_mode: normal | locked` — чёрный кадр/замок → `locked`,
    события не шумят.
- Публичное API (синхронное, дёшево):
  - `get_state() -> dict` — мгновенный снимок;
  - `describe_screen(question) -> str` — подпись: кэш если свежий (TTL),
    иначе живой VLM и обновление кэша;
  - событие/колбэк `on_change_for_watchers()` — для watch-оценки.

### 3.2 Ярус 2 — семантика (переиспользует `look_at_screen`)

- `describe_screen` вызывает существующий `_ask_model_about_image`
  (`actions.py`) с базовым вопросом «Что открыто на экране и в каком
  порядке?».
- Вызывается: (а) при запросе о экране и протухшем кэше; (б) фоновым
  refresh раз в `caption_refresh_s` (default 45с) — подпись всегда не
  старше ~1 минуты; (в) watch-оценкой конкретного окна.

## 4. Встраивание в мозг и агента

### 4.1 Новые действия мозга (whitelist `_LOCAL_ACTIONS`, `local_brain.py`)

- `get_screen_state: {}` — активное окно + недавние события (без VLM);
- `start_watch: {"target": "...", "when": "change|appear|disappear",
  "what": "сообщение при срабатывании", "capture": "title|screen"}`;
- `stop_watch: {"target": "..."}` — удалить наблюдателя;
- `list_watches: {}` — текущие правила.

Системный промпт получает короткие примеры для этих четырёх.

### 4.2 `ws_client.py`

- `_resolve_local_plan`: при запросе модели `look_at_screen` сначала
  пробуем подпись из `caption_cache`; живой взгляд — только при протухшей
  подписи. В переплан подмешивается строка активного окна и недавних
  событий из яруса 1.
- Контекст команд: в `_handle_chat` к промпту добавляется компактная
  строка «🗔 Активно: <окно>; недавно менялось: <…>» из `get_state()`
  (без VLM).
- Старт watcher при запуске приложения.

### 4.3 `actions.py`

- Функция `get_screen_state() -> (status, text)` — обёртка над
  `screen_watcher.get_state()` для `execute_action` (действие
  `get_screen_state`).

## 5. Наблюдатели (watchers)

- Хранилище: `eva_agent/screen_watch_rules.json`, переживает перезапуск.
- Правило: `{id, target, when: change|appear|disappear, what, capture:
  title|screen, created}`.
- Оценка (в `watchers.py`, фоновый поток, на события яруса 1):
  - `when=appear/disappear`: срабатывает при появлении/исчезновении окна
    с заданным target (сопоставление через существующие хелперы
    `_pick_window`/`_find_window` и по class_name).
  - `when=change`: target-окно активно → селективный VLM/OCR по области
    этого окна → сравнение с прошлым снапшотом → при изменении →
    срабатывание.
  - Срабатывание → уведомление в Telegram + приложение существующим путём
    («агент → сервер → ...»), не чаще одного раза в `watch_cooldown_s`
    (default 300) на правило.
- Деградация при недоступной Ollama: appear/disappear работают по ярусу 1
  без VLM; «изменение контента» — через OCR/diff, если возможно.

## 6. Ошибки и деградация

- Ollama недоступна: ярус 1 жив; `describe_screen` возвращает протухшую
  подпись или признак недоступности; watch на change деградирует до
  OCR/diff; чат уже умеет «мозг недоступен».
- Кадр не снимается (sleep/замок): `screen_mode=locked`, события не
  шумят; при возврате — событие unlock.
- Исключение при захвате кадра: ловится в цикле, состояние не портится,
  следующая итерация продолжает.
- Тайминги в `config.py`: `screen_frame_interval`, `caption_ttl`,
  `caption_refresh_s`, `watch_cooldown_s`.

## 7. Ресурсы

- Ярус 1: < 5–10% одного ядра (кадр 320px/сек + win32); на батарее
  интервал поднимается через конфиг.
- Ярус 2: VLM по требованию + refresh раз в 45с ≈ единицы % GPU в
  среднем.
- RAM: кадры не хранятся; ring-buffer событий крошечный.

## 8. Тестирование

- `test_screen_watcher.py`: дифф и пороги (синтетические PIL-кадры),
  детект смены окна (моки win32), TTL кэша, locked-режим.
- `test_watchers.py`: оценка правил (appear/change/disappear) на фейковых
  потоках событий, cooldown, сопоставление target.
- `test_ws_client*`: кэш-путь в `_resolve_local_plan`, инъекция строки окна
  в промпт. Gotcha (из памяти): `ws_client` импортирует
  `list_window_titles` по имени — мокать `"ws_client.list_window_titles"`.
- Интеграция: `get_screen_state` через `execute_action`.

## 9. Что НЕ входит в этот объём

- Самоинициирование без запроса (кроме явных watch-правил).
- Хранение/история скриншотов.
- Удалённый просмотр экрана.
- Многопользовательская маршрутизация (отдельная итерация).
- Проактивные «подсказки» в интерфейсе.
